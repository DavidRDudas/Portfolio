Key fingerprint —

Nobody can eyeball whether they redrew a 12-step pattern correctly, so this is the same trick SSH uses: note the fingerprint down, and next time you draw the key, check it matches before you rely on it. Treat it as secret — it is a hash of the only secret in the system, so anyone holding it can confirm a guessed pattern offline.

The realistic estimate deliberately discounts patterns that look like something a human would draw: a step landing next to the previous one is credited about 3 bits instead of the full log₂(N), and colour and rotation count only where you actually varied them. It is a heuristic meant to be pessimistic, not a proof of strength.

Naor–Shamir visual secret sharing

This is the original “visual cryptography”, published by Moni Naor and Adi Shamir in 1994. There is no key and no computer needed to decrypt: the message is split into two images of pure noise, and stacking them physically reveals it. Your eye does the decryption.

Every pixel of the secret becomes a 2×2 block in each share, chosen from the six blocks that have exactly two black subpixels. If the secret pixel is white both shares get the same block; if it is black they get complementary blocks. Stacking is an OR — ink blocks light — so white recovers as 50% grey and black as solid black.

Does visual encryption actually work?

Yes — but only two of the three things people mean by the phrase are real, and the original version of this app did the third one.

What the legacy method got wrong

The legacy cipher animates a grid, derives 64 bytes of key material from the active cells' positions, colours, rotations and intensities, stretches that through PBKDF2 with up to 225,000 iterations, and encrypts with AES-256-GCM. Every primitive in that sentence is a good one. It is still worth nothing, for three compounding reasons:

  1. The key ships with the ciphertext. analyzeGridPattern() builds a pattern string listing every active cell as position:colour:rotation:intensity. The key bytes are computed from exactly those fields — and then pattern is base64-encoded into the gridState field of the output. decrypt() reads it straight back out and rebuilds the key. There is no secret anywhere in the system.
  2. Nobody chose the pattern. The grid is mutated by a setInterval on a timer. The user never picks it, so it is not something they know and could re-supply later. It is a random key that has to be transmitted — and it is, in the clear.
  3. The second class is worse. SecureVisualGridCipher calls exportKey('raw', ...) and puts the raw AES-256 key in the output as a field literally named key. It is also dead code: encodeText() uses the base class. And its decrypt() reads the AAD from gridState.pattern, which is only written when the “include grid data” box is ticked, so with the box unticked it could never have decrypted its own output.

The general lesson: expensive key derivation protects a secret an attacker has to guess. If the attacker is handed the input to the KDF, iteration count is irrelevant. 225,000 iterations of nothing is nothing.

None of that is a claim you have to take on trust. The Attack Lab tab implements it: paste any legacy envelope and it recovers the plaintext, using a key schedule reimplemented from scratch against the output string alone. It never touches the app's own decrypt() and does not need the grid that produced the ciphertext to still exist — a browser tab that has never rendered the grid decrypts it just as well.

A smaller bug in the same file is worth naming because it is the classic one: getRandomCell() computes Math.floor(byte * gridSize² / 256). On a 32×32 grid that is byte * 4, so it can only ever return cells 0, 4, 8, … — three quarters of the grid are unreachable. Folding random bytes into a range needs rejection sampling, not scaling.

Two more surfaced while building the attacks, both about timers rather than cryptography:

  • startGridAnimation() opened a 250ms setInterval and never kept the handle. The constructor calls it once, script.js calls initializeGrid() again immediately after, and applyGridSettings() calls it once more on every click — so the animation quietly accelerated for the rest of the session, and kept restyling 1,025 cells even with its tab hidden. It now retires the previous timer and pauses when it is not on screen.
  • const secureCipher = new SecureVisualGridCipher(32) ran at script-parse time and was then never referenced by anything. Constructing it started another permanent animation timer and rendered into the same #gridContainer, so a dead object spent every session animating the live grid's cells from underneath the cipher that actually owns them. The instantiation is gone; the class stays as the worked example it is.

The three real meanings of “visual encryption”

1. Visual secret sharing — real, provably secure, and implemented on the Visual OTP tab. Naor and Shamir's 1994 scheme splits an image into shares that are individually indistinguishable from noise; stacking them reveals the secret with no computation. A single share is information-theoretically useless: it is a one-time pad applied to pixels, so it is not merely hard to break, there is nothing there to break. The price is that each share is twice the size of the secret in each dimension, contrast drops by half, and a pad may never be reused.

2. A visual key — real, and what the Visual Key tab does. A drawn pattern is just a password with a nicer input method. It works exactly as well as the pattern is unguessable, which is the entire caveat: humans draw lines, letters and symmetric shapes, so the realistic entropy is far below the theoretical maximum. The strength meter tries to say so honestly rather than flatter you.

3. Steganography — real, but not encryption. Hiding a message in an image's low bits conceals that a message exists; it does nothing to protect the content once found. It composes with encryption, it does not replace it.

What is not real is the fourth thing, which is what the legacy method did: generating randomness locally, deriving a key from it, and shipping the randomness alongside the ciphertext. That is an encoding, not an encryption.

What this build does — VSC-1

Two independent layers. Neither one invents a primitive; inventing primitives is how the legacy cipher happened.

  • Layer 1, the visual key. The drawn pattern is canonicalised to VSC1|gridSize|cell.colour.rotation-…, run through PBKDF2-HMAC-SHA256 with a fresh 16-byte salt, and used as an AES-256-GCM key. The full 38-byte header — version, grid size, iteration count, salt, IV — is passed as additional authenticated data, so an attacker cannot rewrite the iteration count down to 1 to make an offline attack cheap. The pattern is never stored or transmitted.
  • Layer 2, the visual shares. The envelope is XORed with a fresh pad the same length. Share 1 is the pad, share 2 is the XOR. Each is uniformly distributed and independent of the envelope, so one share is genuinely zero information — this is 2-of-2 secret sharing, not obfuscation. Both are rendered as PNGs, three bytes per pixel with alpha pinned at 255 so nothing is lost to premultiplication.

Recovering the message needs share 1, share 2, and the pattern. Any two of the three give you nothing.

Where this is still weak

Stating this plainly is the point of the app, so:

  • The pattern is the whole ballgame. A short or line-shaped pattern falls to an offline dictionary attack over plausible shapes. PBKDF2 at 600,000 iterations adds roughly 19 bits of work — helpful, not redemptive. Attack 2 in the Attack Lab demonstrates exactly this against your own current key: a five-cell horizontal run falls in about 200 guesses, a couple of seconds. Measured on this machine, 600,000 iterations costs the defender only about 97ms, which works out to roughly 10 guesses per second on one JavaScript thread — and a GPU is orders of magnitude faster than that.
  • PBKDF2-SHA256 is GPU-friendly. Argon2id is the right choice for a password-derived key; it is not used here only because it would mean shipping a dependency into a static portfolio page.
  • The two shares must travel separately. Emailing both attachments in one message reduces the scheme to layer 1 alone.
  • Length leaks. The envelope, and therefore each share, is about as long as the message. No padding scheme is applied.
  • Browser JavaScript is not a trustworthy execution environment. Anyone who can modify the page can read your pattern as you draw it. This is a demonstration of a construction, not a tool to protect anything that matters.
  • It has not been reviewed by anyone. For real work use age, libsodium, or Signal — things that have survived people trying to break them.

The Settings tab has a self-test that runs the whole path in your browser: round-trip, wrong-key rejection, single-bit tamper detection, share recombination, the PNG encode/decode cycle, and the Naor–Shamir contrast and uniformity properties.
